# exe.dev 3-VM deployed test (2026-10-05)

Topology: `proxima-e2e` = panel (API + PostgreSQL 16 + Redis 7, `ENFORCE_CONCURRENCY=1`); `proxima-node-a`, `proxima-node-b` = real node-agent + Xray 26.7.28, role `exit`, `publish_direct=true` (no relay). All three VMs: exe.dev Tokyo, shared 2 vCPU / 8 GB trial pool. Client: Xray 26.7.28 on the operator's Mac.

Source: main 74bc476 plus the uncommitted DEP-01 limiter patch and relay-e2e harness changes; binaries cross-built linux/amd64. No production data, keys or `.env` used; all credentials were generated for this disposable panel.

## Networking constraint

exe.dev VMs have no VM-to-VM network and their hostnames resolve to an HTTPS edge proxy, so raw TCP/UDP from outside does not reach a VM port. All links therefore run over SSH tunnels via the Mac:

- Mac:12053 → panel :2053
- node-a/b 127.0.0.1:2053 → Mac:12053 → panel (agent control plane)
- Mac:18443/18444 → node-a/b VLESS port

Consequence: node ↔ panel round trip is ~132 ms (each hop through the Mac in Korea). Node egress to the internet is the VM's own (all VMs share egress IP 64.34.94.211).

## Findings

- **F1 (test artifact, resolved):** an orphaned Xray client from an earlier probe held a SOCKS port and made a working server look broken; rerun on clean ports.
- **F2 (product issue):** Reality target `www.microsoft.com` fails the Reality handshake from these VMs (Akamai edge), while `www.apple.com` works with identical keys/UUID/shortId. Panel then blocks fixing it: changing node `reality_client_sni` returns 409 "incompatible with node listeners", editing the inbound returns 409 "incompatible with the node SNI", deleting returns 409, and a second Reality inbound is rejected. Circular validation forced a direct DB update (`nodes.reality_client_sni` + inbound `dest/server_names` together). Needs an atomic API path to change both.
- **F3 (design limit, important):** speed is bounded by the per-chunk central permit round trip, not by the configured cap. One 32 KB chunk per device/direction in flight → ceiling ≈ 32768·8 / RTT. Measured: download 2.6–2.8 Mbps single and 4-stream aggregate (4 streams do not add), upload 7.4 Mbps, with server-side permit handling p50 3.9 ms / p95 5.1 ms / max 16 ms (1,928 requests, all 200). At 132 ms RTT the ceiling is ~2 Mbps; at 5 ms it would be ~52 Mbps; at 20 ms ~13 Mbps. Production nodes far from the panel will not reach plan speeds. Fix needs pipelined/prefetched grants or a local token bucket refilled by the panel.
- **F4 (environment):** exe.dev cannot host a realistic multi-node network test (no VM-to-VM, no raw public ports). Real cross-VM latency, public Reality exposure and throughput need ordinary VPS hosts.
- **F5 (record):** a teammate reported a 2 s snapshot watchdog; this build uses 5 s, and test 9 observed ~5 s.

Not covered: real VPN client apps / x-hwid import flow; multi-hour soak; production-scale load; public-internet exposure of node ports.
