# exe.dev deployed test, round 2 (2026-10-05)

Changes under test (uncommitted): node-local speed limiting (no panel in the data path), atomic Reality target API, plus round-1 limiter/harness patches.

## exe.dev facts (from docs and measurement)

- Regions: PDX, LAX, NYC, DAL, FRA, TYO, SYD, SGP, LON. Region is per account (`set-region`) or per pool; `new` has no region flag. Closest to the operator (KR) is **TYO**, which this account already uses; all 3 VMs are in TYO.
- Latency from the operator's Mac (KR, 121.134.x) to TYO VMs: ICMP 35–39 ms; TCP connect to edge 37.9 ms; SSH echo round trip 40.8 ms.
- VMs have no public IP of their own ("we don't give your VM its own public IP"). DNS IPs are exe.dev's edge (TCP refused on non-HTTP ports); outbound egress is a shared NAT IP (64.34.94.211) that accepts nothing inbound. Verified: raw TCP/UDP VM→VM on either IP fails. Only HTTPS (edge proxy) and SSH (`vm.exe.xyz`) are reachable.

## Topology this round

- Node → panel control plane: SSH tunnel **directly VM-to-VM** (node VM keys registered with `ssh-key add`; systemd `px-panel-tunnel` on each node). Node→panel RTT 16–17 ms. The Mac is not involved.
- Mac = VPN client only. Because exe.dev exposes no raw VM port, the client reaches each node's VLESS port through `ssh -L` to that node (Mac→node directly, no hop through the panel). On a normal VPS the client would connect straight to the node IP.

## Known trade-off (accepted)

Speed is now metered per Exit. One device attached to two Exits simultaneously can use up to the plan rate on each. Concurrency/UUID-slot admission is still central and unaffected.
